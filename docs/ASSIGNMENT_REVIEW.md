# 作业设计审查与修订建议

## 结论

题目方向成立，也能覆盖 MCP、异步 I/O、信息检索、LLM Agent 和工程评测；但现有版本把“协议层、业务编排层、模型推理层”混在了一起。若按原分工直接开工，最可能出现三类问题：接口互相等待、Top-k 定义前后不一致、Demo 能跑但无法公平比较优化效果。

## 主要问题

### 1. 主 Agent 与 MCP 内“任务 Agent”职责重叠

MCP 是能力暴露协议，不要求服务内部必须再有 Agent。主 Agent 已负责理解用户意图和调用工具，如果 MCP Server 内部又放一个自由规划的任务 Agent，谁负责查询改写、筛选、失败重试和停止条件会变得不清楚，调试也无法复现。

建议：MCP Server 暴露边界清晰、输入输出结构化的工具；服务内部需要 LLM 时，将它作为 `QueryPlanner`、`EvidenceVerifier`、`ReportWriter` 等可替换组件，而不是第二个不受约束的总控 Agent。

### 2. “基础排序—二次筛选—最终重排”定义重复

三个阶段都在做相关性判断，但原要求没有规定各阶段使用的数据、成本和目标。最终会出现三个组都写一套相似的提示词。

建议明确：

| 阶段 | 可用证据 | 目的 | 输出规模 |
|---|---|---|---|
| 基础排序 | 标题、摘要、关键词 | 低成本降噪 | 全部候选 → N |
| 全文证据确认 | 章节、图表说明、实验段落 | 排除“摘要看似相关、正文不支持” | N → M |
| 最终重排 | 全文证据、用户侧重点、时效与质量 | 形成可解释 Top-k | M → k |

### 3. 先固定 Top-k 再下载全文会造成名额浪费

Top-k 中可能有闭源、链接失效、非 PDF 或解析失败项。若只下载这 k 篇，就无法自动补位。

建议先生成较大的全文处理池 `N`（如 `max(4k, 20)`），并发下载和解析；失败后由候补论文补位，最后再形成 Top-k。若允许摘要降级，报告必须标注“基于摘要”，不可与全文证据混同。

### 4. 数据源选择与“公开、免费、稳定”要求冲突

- Google Scholar 没有面向本作业的官方公开检索 API，直接爬取稳定性和合规性风险较高。
- 知网并非免费开放全文来源，授权、验证码和下载权限会破坏可复现实验。
- Crossref 主要解决 DOI 和出版元数据，不等于全文下载源。
- “返回 BibTeX 再转 Model”会丢失 OA 状态、来源冲突、抓取时间、解析质量等业务字段。

建议基线使用 arXiv + OpenAlex 或 Semantic Scholar；Crossref 用于 DOI 补全，Unpaywall/开放仓储用于 OA 定位。适配器直接返回统一 `Paper`，BibTeX 只作为可选原始字段保留。

### 5. 去重规则过于笼统

仅按标题去重会误合并同名论文，也会漏掉预印本、会议版和期刊扩展版。

建议分层匹配：DOI 精确匹配 → arXiv ID 精确匹配 → 规范化标题 + 第一作者 + 年份 → 模糊标题候选人工/模型确认。合并时保留所有来源记录和字段冲突，不覆盖原始证据。

### 6. “相关性”和“排序质量”没有可操作的金标准

如果没有人工标注查询集，优化前后 Top-k 相关性只能靠主观展示，不能构成实验。

建议准备 15–30 条不同领域研究想法，由至少两名组员独立标注候选论文相关等级（0/1/2/3），记录一致性；使用 nDCG@k、Recall@k、MRR。任务成功率需定义各阶段成功条件；运行时间报告 P50/P95，并固定候选规模、缓存状态和并发度。

### 7. “任选一个优化”之间不可直接横向比较

增加数据源、排序优化、并发优化分别改善覆盖率、质量、速度。只给一个总指标会对部分选项不公平。

建议设共同指标（端到端成功率）加专项指标：

- 数据源：Recall@k、唯一有效论文数、OA 命中率；
- 排序：nDCG@k、MRR、人工偏好胜率；
- 并发：总耗时 P50/P95、吞吐量、错误率和限流次数。

### 8. 缺少失败语义、缓存与可追溯性

真实论文 API 会超时、限流、字段缺失、PDF 伪装和解析失败。若只返回一个列表，UI 无法解释部分成功。

本项目模型增加了：阶段状态、错误码、警告、来源记录、评分拆解、解析器版本、文件哈希、解析质量以及证据定位。建议检索结果和 PDF 使用内容缓存，失败采用有上限的指数退避，并遵守来源速率限制。

### 9. 分工边界仍有交叉

- “关键词提取”属于查询规划，不宜仅归检索组而主 Agent 又做一次。
- “并发总结”由处理组实现，但报告生成在排序组，二者共享 LLM 调用、限流与证据格式。
- 总体架构一人承担 MCP、UI、接口和联调，风险过于集中。

建议总体负责人只拥有领域模型、接口、编排器和集成测试；每组拥有自己的适配器与单元测试。UI 可由文档/展示成员提前接入模拟数据，而不是等项目全部完成。

### 10. “自行编写 MCP SDK”表述不准确，Nature Skill 也不应成为核心依赖

学生应当“使用官方 MCP SDK 自行编写 MCP Server”，而不是自行实现 SDK 或协议，否则作业重点会偏离论文检索。Nature Skill 可以作为写作风格或绘图扩展，但第三方 Skill 的提示词、脚本、依赖和许可证应先审查；核心验收不应依赖它，否则难以保证可复现性和安全边界。

## 推荐验收口径

1. 至少两个真实、可复现的数据源适配器。
2. 一条查询即使某一来源失败，仍能返回 `partial` 结果并说明原因。
3. 每篇最终论文显示来源、去重依据、各项得分、全文/摘要证据状态。
4. 下载只针对合法公开全文，禁止绕过付费墙。
5. 摘要和报告中的关键结论能定位到论文、页码或 Markdown 锚点。
6. 固定测试集运行优化前后实验，并保存配置、随机种子、缓存状态与版本。
7. MCP Inspector 和 Streamlit Demo 均可复现同一核心流水线结果。
